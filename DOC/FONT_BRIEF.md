# S6ED — Font Asset Brief

S6ED is an MSX2 text editor running in SCREEN 6 (512x212, 4 colours). It renders
text as an 80 x 24 character grid with a 6 x 8 pixel cell. This brief describes
the asset we need: a 256-glyph bitmap font in four weights — normal, bold,
italic and bold-italic.

> **Round two.** Normal is done and in the editor. The sheet has grown to four
> blocks, and the three new ones arrive **pre-filled with a machine derivation
> of your normal weight**, so the job is retouching rather than drawing 756
> glyphs from scratch. See *Layout* and *The column 5 rule*.

## Files

| File | What it is |
|------|------------|
| `RES/FONTSHEET.SR6` | **The working file.** Raw SCREEN 6 VRAM page, 27136 bytes. Open in SRView. |
| `RES/FONTSHEET.PNG` | The same pixels as an 8-bit indexed PNG, for PC tools. |
| `RES/FONTSHEET.PL6` | Companion palette. A raw `.SRx` carries no palette of its own. |
| `RES/FONTGUIDE.SR6` `.PNG` `.PL6` | **Reference only.** A single labelled grid with guides, the four weights sampled and the rules painted on. Do not draw on this one. |
| `RES/mkfontsheet.py` | Regenerates all of the above. |
| `RES/fontcheck.py` | Reads an edited sheet back, checks it and writes `FONT.BIN`. |

Return the edited **FONTSHEET**, in either format, same dimensions, same layout.

### About the palette

A raw `.SRx` file is pixels only. A viewer that does not load the companion
`.PL6` falls back to the MSX default palette, where entry 0 is *transparent*.
The working sheet therefore uses only entries 1 (background) and 3 (ink), so it
stays legible either way. Keep drawing in those two.

## Layout

The sheet is 512 x 212 and carries **four blocks** of 256 x 64, two by two:

```
            x 0                        x 256
    y  20   NORMAL                     BOLD
    y  96   ITALIC                     BOLD+ITALIC
```

Inside its own block a glyph sits exactly where the editor blits it from:
**glyph N at `((N & 31) * 8, (N >> 5) * 8)`**, rows running `+00 +20 +40 +60
+80 +A0 +C0 +E0` top to bottom. Two blocks side by side come to 512 pixels
exactly, so there is no gap between them and no room for the row labels —
`FONTGUIDE` keeps the single labelled grid for looking codes up.

The thin blue rules and the block titles are chrome. They live in the gaps
between blocks and on column 7 of the last cell of each left-hand block, which
is never drawn, and the importer reads them as chrome rather than ink. You can
ignore them; you cannot usefully draw on them.

Each block converts straight back with no re-layout step:

```
python3 RES/fontcheck.py RES/FONTSHEET.SR6 --variant normal     --out RES/FONT.BIN
python3 RES/fontcheck.py RES/FONTSHEET.SR6 --variant bold       --out RES/FONTB.BIN
python3 RES/fontcheck.py RES/FONTSHEET.SR6 --variant italic     --out RES/FONTI.BIN
python3 RES/fontcheck.py RES/FONTSHEET.SR6 --variant bolditalic --out RES/FONTBI.BIN
```

`--variant` sets both the block origin and that block's column rules.

`fontcheck.py` exits non-zero if any rule below is broken, so it can gate a
build. Run it before sending anything back.

The NORMAL block holds the weight you already drew. The other three hold a
machine derivation of it, generated by the same transforms the engine would
have used. They are a starting point with the right width and rhythm — retouch
them, do not feel bound by them.

Note the cells are 8 pixels wide but only the first 6 are ever drawn on screen.
Anything in columns 6-7 is silently discarded on import.

## The column 5 rule

It is now **per block**, and this is the whole point of the change:

| Block | Columns you may use |
|---|---|
| **NORMAL** | **0-4 only. Column 5 must stay empty.** |
| BOLD, ITALIC, BOLD+ITALIC | 0-5. Column 5 is yours. |

In NORMAL the empty column is the letter spacing. The renderer copies 6 pixels
per cell and advances 6, so column 5 *is* drawn: ink there touches the next
character and a wall of running text stops reading.

The three variants no longer have to leave that column free, because they are
no longer derived from NORMAL at run time — they are your own artwork, loaded
from VRAM as separate tables. Bold text has no gap between letters at a 6 pixel
pitch, which is expected and not something to design around; but now *you*
decide which strokes thicken, rather than a machine smearing every one of them
one pixel right.

Columns 6-7 are never drawn, in any block, and are silently discarded on
import.

### Why the pre-fill looks the way it does

**Bold** thickens one pixel right, masking out any background pixel with ink on
*both* sides so one-pixel counters survive. The naive `row | (row >> 1)` closes
a counter in **37 of the 95 printable glyphs** — `A M N W m n u v w` and
friends turn into blobs; the masked version damages 0 of 95. Keep interior gaps
at one pixel or more and they will be preserved.

**Italic** leans the top half one pixel right. At 8 rows in a 6 pixel cell that
is a lean, not a slant — this is the block where hand-drawn letterforms (a
single-storey `a`, a curved `f`) buy the most.

**Bold+italic** is the weak one, unavoidably. Italic lifts column 4 into column
5 and bold then has nowhere left to grow, so the thickening falls off into
column 6 and is discarded: **427 pixels lost across 91 of the 95 printable
glyphs**, and two come out identical to plain italic. Six pixels do not hold
both transforms. **Redraw this block first** — it is the one where the
derivation has least to offer.

### Why the bold transform will not eat your counters

The obvious way to embolden a bitmap is `row | (row >> 1)`. Measured against the
stock MSX ROM charset, that closes a one-pixel counter in **37 of the 95 printable
glyphs** — `A M N W m n u v w` and friends turn into blobs. S6ED instead masks
out any background pixel that has ink on *both* sides, so one-pixel holes
survive: 0 of 95 damaged. The rule is structural rather than tuned to one
typeface, so it holds for whatever font you draw — but keep interior gaps at one
pixel or more and they will be preserved.

## Vertical metrics

Eight rows per cell. Follow the reference:

- Rows 0-6: capitals and x-height.
- Baseline on row 6.
- Row 7: descenders only (`g j p q y`, and the comma and semicolon tails).

There is no blank separator row, so adjacent text lines touch where a descender
occurs. Normal for a 6 x 8 MSX font.

## Colour

None. The sheet is monochrome: a pixel is either ink or background. The editor
picks the colour at draw time — the same glyph is used for normal text, for
syntax highlighting and for the UI chrome. Do not encode colour in the glyphs.

## Character set

All 256 codes, in each of the four blocks. Priority order if time is short:

1. `#20`-`#7E` — printable ASCII. This is what the editor shows 99% of the time.
2. `#80`-`#FF` — accented characters and box drawing. The MSX ROM set is
   localised per machine, which is the main reason we want our own font.
3. `#00`-`#1F` — control range. Currently unused by the editor; leave as-is or
   use for editor symbols (tab marker, end-of-line marker, cursor shapes).

## Style notes

It is a code and prose editor, shown at 80 columns on a CRT. Legibility at
small size beats personality. Specifically:

- Keep strokes one pixel where possible. The font previously bundled with S6ED
  (a cartridge boot-menu display face) used two-pixel left stems and read
  lopsided and cluttered.
- `0` / `O`, `1` / `l` / `I`, `5` / `S`, `8` / `B` must be distinguishable.
- Punctuation matters more than usual: `; : , . ' " ( ) [ ] { } < >` all carry
  meaning in source code.
